# 通用中间工具想法

## 背景

协议已经靠差分+抓包大致清楚了，但实验方式还是：
- 每次想要试一个响应构造/字段语义，都得改模拟服务器代码，再重启服务器，有时还得重启客户端
- 变量多、组合多、状态依赖多时，这种“猜+重启”方式成本高、效率低

所以想做一个**放在客户端和模拟服务器之间的中间工具**，用来降低试验成本。

如果实战中发现每次试一个假设都要重启客户端或模拟服务器，代价就更大。这时候“哪种手段能把目标客户端单独拎出来”比“代理服务器自己做什么”更关键。

## 目的

- 减少每次试验都重启客户端与模拟服务器的成本
- 在客户端和模拟服务器之间插入一层，可以截获、查看、修改、重发请求与响应
- 让“试一个响应构造”不依赖改模拟服务器代码后重启服务器，也不依赖频繁重启客户端
- 为后续更复杂的协议实验保留结构：记录、回放、改包、对比

## 核心能力

1. **代理服务器形态**
   - 自身作为代理服务器，客户端/中转流量发给它，它再转给后端模拟服务器或客户端
   - 能收请求、收响应、发请求、发响应

2. **转发**
   - 客户端的请求先到中间工具，再转给模拟服务器
   - 模拟服务器的响应先到中间工具，再转给客户端
   - 保持双向可达，不破坏 UDP 语义（这里是 UDP，所以不处理粘包/分帧问题）

3. **记录**
   - 记录请求和响应的原始字节、来源/目标地址、时间、序号
   - 最好能按“一次往返”配对保存，方便后续对比和回放

4. **查看**
   - 实时或事后能看 hexdump、字段解析（如果已知协议头就初步解析）
   - 能快速判断客户端有没有收到服务器响应、收到的是什么

5. **修改**
   - 可以临时改请求再转发给服务器
   - 可以临时改服务器响应再转发给客户端
   - 支持“试一个字段/构造”时不用重启两端

6. **构造/回复**
   - 能在不依赖后端服务器真实返回的情况下，构造响应发给客户端
   - 能试不同的响应构造、状态值、长度、方向字节等

7. **重发/回放**
   - 能重发某次请求或某次响应
   - 能回放以前保存的请求-响应记录，用于回归或构造验证

8. **可扩展性**
   - 初始针对 UDP 简单包，但设计上不要把“固定协议解析”硬编码死
   - 协议解析可以后期加载/配置，以免中间工具变成另一个只能试这种 calc 协议的脚本

## 不要走入的误区

- 中间工具不是用来代替协议分析的。它不能代替你搞清楚响应应该长什么样。
- 中间工具也不是万能重启替代品。如果客户端校验 very strict，或者有加密/签名/状态窗口，中间工具有用，但问题可能还是得通过客户端侧分析来解决。
- 不要一开始就给它加太多协议特定逻辑。先做“可转发、可记录、可改、可重发”的骨架。
- 不要把进程筛选/定向这件事强加给中间代理服务器自己去做。代理服务器可以只管转发+改包+记录，由上游手段负责把目标进程的流量引过来。

## 对于当前 calc 项目的最小可用目标

- 客户端发请求 → 中间工具记录 → 转给模拟服务器 → 记录响应 → 转给客户端
- 能够在中间临时改响应并发给客户端，不重启客户端和模拟服务器
- 能够看到客户端实际收到的响应字节
- 最好能保存几次往返记录，供回放或对比

## 后续 发展方向

- 加入简单的响应模板/构造器，让你能快速试不同 type/status/value 而不改服务器代码
- 加入回放模式：把保存的请求再发一遍，观察客户端反应
- 如果协议变复杂，逐步增加协议解析配置、包过滤、重放控制
- 如果后面需要更强的改包能力，再考虑接入更通用的抓包/代理工具或自己写浅层代理

## 暂时搁置的问题

- 是否一定要支持 TCP/分片/重传/加密等复杂情况（当前项目不需要，但未来可能需要）
- 是否需要图形界面（初期命令行/日志足够应该没问题）
- 是否需要做成通用代理而不是项目定制工具（先满足当前实验需求，再看是否通用化）

## 能用的实现手段（补充）

目标是把 calc_gui.exe 的流量引到中间代理服务器上，供中间工具截获、修改、构造、转发。不在中间代理服务器上硬做进程筛选。

### 1. 加载 DLL 到目标进程

- 挂到 calc_gui.exe，在目标进程内截获发送函数（例如 sendto / WSASendTo，或更上层封装）
- 在回调里把目标 IP/端口改到代理服务器，或者把数据送给另一个本地组件
- 接收侧也可截获，用于查看客户端实际收到的响应
- 适合“只能针对单个程序”的情况

### 2. 系统层面按进程筛选/重定向

- 用支持按进程筛选的工具，把只有该进程的流量导到中间代理服务器
- 不让所有程序流量都进来，避免被无关流量淹没
- 代理服务器本身不负责进程筛选，只负责转发+改包+记录

### 3. 改客户端服务器地址/端口

- 如果客户端可以设服务器地址，就直接让它指向中间工具
- 这是最简单的入口，但依赖客户端配置可改

### 4. 其他入口（保留选项）

- 本机端口/目标重定向
- 更底层的按进程/端口/协议拦截框架
- 全局走代理仅在必要时考虑，通常代价大

### 重点

- 进程定向这件事，可以由 DLL 或系统侧工具来做，代理服务器不一定非要自己实现
- 中间代理服务器的职责应集中在：接收流量、记录、改包、构造响应、转发给模拟服务器或客户端
- 不要假设代理本身会自动让所有程序都经过，除非真的需要那种范围
